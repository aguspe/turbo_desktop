Features

Everything you need to turn your Rails app into a native desktop application — with zero new UI code.

🖼

Multi-Window Management

Main, modal (800×600), and new window (1200×800) presentations. Dynamic title sync, window state queries, and label-based close.

🧭

Path Configuration Routing

JSON rules with regex patterns (last-match-wins). Six presentation types: default, modal, new_window, replace, native, none. Same concept as turbo-ios.

🌐

Turbo Drive Integration

Intercepts turbo:before-visit, turbo:load, turbo:frame-load, and turbo:submit-start. Visit proposals routed through Rust.

📡

Bridge Components

A dozen built-in native components: notifications, menus, file pickers, filesystem, shell, sudo, clipboard, autostart, badges, shortcuts and more. Extensible via event forwarding.

🚀

Server Auto-Start

Opening the app starts your Rails server too, through a login shell so rbenv/asdf/mise just work. A server you started yourself is left alone.

📂

Files, With Consent

The filesystem bridge is scoped to roots you declare — but a path the user picks in a dialog, drops on the window, or opens with the app is consent, and just works.

🪂

Drag & Drop + File Associations

Dropped files arrive as DOM events with real paths. Declare file types and double-clicking a file opens your app with it — even from a cold start.

📋

Clipboard & Autostart

Read what any application copied, write without a page gesture. Offer a launch-at-login toggle backed by the OS: Launch Agent, registry Run key, or XDG entry.

🔐

Privileged Commands

An allowlisted sudo bridge elevating through each platform's own prompt: the macOS password dialog, polkit on Linux, UAC on Windows.

📋

Native Menu Bar

Full macOS menu bar: App, File, Edit, View (reload, DevTools, zoom), Navigate (back/forward), and Window menus with standard shortcuts.

💎

Rails Gem

turbo_desktop-rails on RubyGems. UA detection, platform/arch helpers, conditional rendering, bridge data attributes, and path config endpoint.

🛠

CLI Scaffolding

npx turbo-desktop init generates the full Tauri shell. dev and build commands with target architecture support.

🧪

Stimulus Bridge Helper

TurboDesktop.stimulusBridge(Controller, name) mixin. Adds sendBridge() and receiveBridge() to any Stimulus controller.

🔍

Developer Tools

DevTools toggle via menu (Cmd+Alt+I) or JS API. Structured logging with RUST_LOG. Hot reload in dev mode via cargo tauri dev.

JavaScript API

The injected window.TurboDesktop object exposes the full native bridge:

TurboDesktop.version          // "0.2.1"
TurboDesktop.isNative          // true
TurboDesktop.proposeVisit(url, action)          // Send visit to Rust shell
TurboDesktop.setTitle(title)                     // Update window title bar
TurboDesktop.sendBridgeMessage(component, event, data) // Bridge message
TurboDesktop.getWindowInfo()                     // Window state (size, pos, scale)
TurboDesktop.closeModal(label)                   // Close modal by label

TurboDesktop.fs.read(path) / .write(path, content) // Scoped filesystem
TurboDesktop.shell.spawn(id, cmd, args)           // Child processes, streamed
TurboDesktop.sudo.execute(cmd)                    // Allowlisted elevation
TurboDesktop.clipboard.readText() / .writeText(t) // System clipboard
TurboDesktop.autostart.enable() / .isEnabled()    // Launch at login
TurboDesktop.dragDrop.onDrop(cb)                  // Files from the desktop

Dropped files and OS-opened files also arrive as plain DOM events — turbo-desktop:drop and turbo-desktop:file-open — so a Stimulus data-action is all a page needs.

How It Works

1

The Tauri shell loads your Rails URL

On launch, Rust reads turbo-desktop.config.json for your server_url (falls back to localhost:3000), sets a custom User-Agent (Turbo Desktop/0.2.1 (macOS; aarch64)), and navigates the 1200×800 main window to your app. 

// main.rs — startup
let app_config = window::load_config(None);
let url: url::Url = server_url.parse().expect("Invalid server URL");
main_window.eval(&format!("window.location.replace('{}')", url));
2

turbo-desktop.js is injected on every page load

The on_page_load callback fires after each navigation completes, injecting the bridge script that creates window.TurboDesktop with the full native API. Double-injection is prevented automatically. 

// main.rs — injection
.on_page_load(|webview, payload| {
    if let PageLoadEvent::Finished = payload.event() {
        let js = include_str!("../../src/turbo-desktop.js");
        let _ = webview.eval(js);
    }
})
3

Turbo Drive events are intercepted

The injected JS listens for turbo:before-visit. Instead of letting Turbo navigate directly, it sends a visit proposal to the Rust shell via Tauri's invoke IPC. It also tracks turbo:load, turbo:frame-load, and turbo:submit-start for full lifecycle awareness. 

// turbo-desktop.js
document.addEventListener("turbo:before-visit", async (event) => {
  const url = event.detail.url;
  const response = await TurboDesktop.proposeVisit(url, "advance");

  // If the native shell handled it, cancel the Turbo visit
  if (response.action === "none") {
    event.preventDefault();
  }
});
4

Path configuration determines presentation

Rust matches the URL against path configuration rules (regex, last match wins) and returns one of six presentation decisions. The path config is fetched asynchronously from your Rails server at startup. 

// navigation.rs
match properties.presentation {
    Presentation::Default   => /* navigate in current window */,
    Presentation::Modal     => /* open a new 800×600 modal window */,
    Presentation::NewWindow => /* open a separate 1200×800 window */,
    Presentation::Replace   => /* replace, no back navigation */,
    Presentation::Native    => /* emit event for native Rust screen */,
    Presentation::None      => /* do nothing (bridge handles it) */,
}
5

Bridge components enable web-to-native communication

Stimulus controllers extend BridgeComponent and call send() to invoke native features. Rust handles the five built-in components and forwards unknown ones as generic bridge-message events for custom handling. Learn more in the Bridge Components section.

Path Configuration

The path configuration maps URL patterns to presentation rules — the same concept from turbo-ios and turbo-android. Fetched asynchronously from your Rails server at app startup.

path-configuration.json
{
  "settings": {
    "screenshots_enabled": true,
    "pull_to_refresh_enabled": false
  },
  "rules": [
    {
      "patterns": ["/"],
      "properties": { "presentation": "default" }
    },
    {
      "patterns": ["/new$", "/edit$"],
      "properties": {
        "presentation": "modal",
        "title": "Edit"
      }
    },
    {
      "patterns": ["/reports/"],
      "properties": { "presentation": "new_window" }
    },
    {
      "patterns": ["/settings"],
      "properties": { "presentation": "native" }
    }
  ]
}

Presentation Types

ValueBehavior
defaultNavigate in the current window. Turbo Drive handles it normally.
modalOpen the URL in a new modal-style window (800×600). The JS visit is cancelled.
new_windowOpen the URL in a full separate window (1200×800).
replaceReplace the current page with no back-navigation history entry.
nativeEmit a native-screen-requested event for fully native Rust UI.
noneDo nothing — navigation handled entirely by a Bridge Component.

Rule Matching

Patterns are regular expressions matched against the URL path using regex-lite. Rules are evaluated in order and the last match wins — identical to Hotwire Native. The configuration store is thread-safe (RwLock) and supports per-route properties like title, pull_to_refresh_enabled, and arbitrary context data.

Bridge Components

The Bridge is the desktop equivalent of Strada. It lets your web components talk to native OS features through structured message passing via Tauri's invoke IPC.

The Flow

  1. A Stimulus controller extends BridgeComponent (or uses the stimulusBridge mixin)
  2. It calls this.sendBridge("connect", { title: "Export" })
  3. turbo-desktop.js forwards this to Rust via Tauri's invoke("handle_bridge_message", ...)
  4. Rust routes the message by component name to the built-in handler (or forwards it as a generic event)
  5. When the native side triggers (e.g., menu clicked), it emits back via send_bridge_response
  6. The web component receives it via receiveBridge(message)

Built-in Components

notification

Show native OS notifications with title and body. Uses tauri-plugin-notification.

menu-item

Register and unregister items in the native menu bar. Supports connect/disconnect events and keyboard shortcuts.

file-picker

Open native file-open and file-save dialogs via tauri-plugin-dialog. Supports open and save events.

badge

Set the dock badge count on macOS. Uses Cocoa/ObjC private APIs directly.

shortcut

Register global keyboard shortcuts with accelerator strings (e.g., Cmd+Shift+N).

filesystem

Read, write, list, mkdir and remove — inside the roots you declare, plus any path the user granted through a dialog, a drop or an OS file-open.

shell

Spawn child processes through the user's login shell (version managers included), with stdout/stderr streamed back line by line.

sudo

Run allowlisted commands elevated through the platform's own prompt: macOS password dialog, polkit on Linux, UAC on Windows.

clipboard

The system clipboard past webview limits: read what any application copied, write without a user gesture.

autostart

Launch at login, meant for a visible settings toggle — recorded with the OS, never enabled silently.

file-open

Files the OS asked the app to open — double-click on an associated type, "Open With…", dock drop — queued through launch and drained by the page.

Unknown component names are automatically forwarded as bridge-message events, making the system fully extensible without modifying Rust code.

JavaScript: Stimulus Bridge

app/javascript/controllers/notification_bridge_controller.js
import { Controller } from "@hotwired/stimulus"

export default class extends TurboDesktop.stimulusBridge(Controller, "notification") {
  connect() {
    super.connect()
    this.sendBridge("connect", { title: "My App" })
  }

  notify(event) {
    this.sendBridge("connect", {
      title: "New Message",
      body:  event.target.dataset.body
    })
  }

  receiveBridge(message) {
    console.log("Native says:", message)
  }
}

Rust: Handling Bridge Messages

src-tauri/src/bridge.rs
#[tauri::command]
pub async fn handle_bridge_message(
    app: tauri::AppHandle,
    message: BridgeMessage,
) -> Result<serde_json::Value, String> {
    match message.component.as_str() {
        "notification" => handle_notification(&app, &message).await,
        "menu-item"   => handle_menu_item(&app, &message).await,
        "file-picker" => handle_file_picker(&app, &message).await,
        "badge"       => handle_badge(&app, &message).await,
        "shortcut"    => handle_shortcut(&app, &message).await,
        _ => {
            // Forward unknown components as events
            app.emit("bridge-message", &message)?;
            Ok(serde_json::json!({ "status": "forwarded" }))
        }
    }
}

Rails Gem

turbo_desktop-rails (on RubyGems) gives your Rails app awareness of the desktop shell, exactly like turbo-rails does for Turbo Native mobile apps.

Installation

# Gemfile
gem "turbo_desktop-rails"
bundle install
rails generate turbo_desktop:install

Detection

Detects desktop app requests via the User-Agent header. The Tauri shell sends Turbo Desktop/0.2.1 (macOS; aarch64). The detection pattern is configurable.

View Helpers

HelperDescription
turbo_desktop_app? Returns true if the request comes from a Turbo Desktop shell.
turbo_desktop_platform Returns "macos", "windows", "linux", or nil.
turbo_desktop_arch Returns "aarch64", "x86_64", or nil.
turbo_desktop_only { } Renders the block only when inside the desktop app.
turbo_web_only { } Renders the block only for regular web (non-desktop) users.
turbo_desktop_bridge(component, **opts) Outputs data-turbo-desktop-bridge attributes for bridge components.

CLI Tool

The turbo-desktop CLI scaffolds the full Tauri shell into any Rails project and provides dev/build commands.

npx turbo-desktop init [path]

Generates the desktop/ directory with all Rust source files (main.rs, config.rs, navigation.rs, bridge.rs, menu.rs, window.rs), Cargo.toml, tauri.conf.json, turbo-desktop.js, and a turbo-desktop.config.json pre-configured for your app.

npx turbo-desktop dev

Starts the Tauri dev server with hot reload. Auto-detects config in current dir or ./desktop/. Sets RUST_LOG=turbo_desktop=info for structured logging.

npx turbo-desktop build [--target arch]

Builds a production binary. Defaults to aarch64-apple-darwin. Supports any Rust target triple via the --target flag.

Example: Add Desktop to an Existing Rails App

# From your Rails project root
npx turbo-desktop init

# Edit the generated config
vi desktop/turbo-desktop.config.json

# Start developing
npx turbo-desktop dev

Turbo Desktop vs Electron

Electron is the most popular desktop framework. Turbo Desktop takes a fundamentally different approach — here’s how they compare.

Feature Comparison

Feature Turbo Desktop Electron
Binary size ~5–10 MB (OS WebView) ~150–300 MB (bundles Chromium)
Memory usage Lower (shared OS WebView) Higher (dedicated Chromium per app)
Backend language Rust Node.js
Frontend Your existing Rails views (server-rendered HTML) Any (typically React, Vue, etc.)
Architecture Server-driven — Rails is the source of truth Client-side — UI logic lives in the Electron app
New UI code needed Zero — reuse existing views Typically full rewrite of UI in React/Vue
Routing Path configuration (JSON, regex) Custom (React Router, etc.)
Web-to-native bridge Bridge Components (Strada pattern) contextBridge + ipcRenderer
Native menus Built-in macOS menu bar with standard shortcuts Full menu API (all platforms)
Notifications Built-in bridge component Chromium Notification API + native
File dialogs Built-in bridge component dialog module
Auto-updater Not yet (planned) Built-in (electron-updater)
Offline support Not yet (requires server) Full (can bundle entire frontend)
System tray Not yet (planned via Tauri plugin) Built-in Tray API
Cross-platform macOS, Windows, Linux — installers for all three on every release macOS, Windows, Linux
Ecosystem maturity New (v0.2.1) Mature (since 2013)
Rails integration First-class gem with detection, helpers, path config None — DIY
Hotwire Native parity Same patterns as turbo-ios and turbo-android Different paradigm entirely

Pros & Cons

Turbo Desktop Strengths

  • Zero new UI code — ship your existing Rails views as a desktop app
  • Tiny binaries (~5–10 MB vs ~200 MB for Electron)
  • Low memory footprint using the OS WebView
  • Same mental model as turbo-ios and turbo-android — one pattern for all platforms
  • Server-driven architecture means instant updates without app releases
  • Rust backend provides memory safety and high performance
  • First-class Rails integration with gem, helpers, and detection
  • Path configuration is declarative and easy to reason about
  • Bridge components are extensible — unknown components forwarded as events
  • CLI scaffolding gets you from zero to running in minutes

Turbo Desktop Limitations

  • Requires a running server — no fully offline-capable apps (yet)
  • macOS-only UI polish today (Windows/Linux architecture ready but not refined)
  • No auto-updater (planned — Tauri has a plugin for this)
  • No system tray support (planned — Tauri has a plugin for this)
  • No deep filesystem access beyond file dialogs
  • No native database (SQLite, etc.) — relies on Rails backend
  • Smaller ecosystem and community vs Electron's 10+ years
  • WebView rendering differences across OS versions (vs Electron's consistent Chromium)
  • No protocol handler registration (custom URL schemes)
  • New project — APIs may evolve before 1.0

When to Choose Turbo Desktop

Turbo Desktop is the right choice when you already have a Rails app and want to give your users a native desktop experience without rewriting your UI. It excels when:

  • Your app is server-rendered with Turbo Drive and Stimulus
  • You already use (or plan to use) Hotwire Native for mobile
  • You want fast deployment cycles — update the server, users get the changes immediately
  • Binary size and memory usage matter (embedded, low-spec machines, enterprise deployment)
  • You don’t need full offline support or heavy client-side state

When to Choose Electron

Electron is better suited when:

  • Your app needs to work fully offline with bundled client-side logic
  • You need consistent cross-browser rendering (Chromium everywhere)
  • You require deep Node.js integration (filesystem, databases, native modules)
  • Your UI is already built in React/Vue/Angular with no Rails backend
  • You need mature auto-update, crash reporting, and code signing tooling

How It Relates to turbo-ios and turbo-android

Turbo Desktop is the third leg of the Hotwire Native story. Same patterns, different platform.

Concept turbo-ios turbo-android Turbo Desktop
Shell runtime WKWebView (Swift) WebView (Kotlin) Tauri WebView (Rust)
Path configuration JSON, last-match-wins JSON, last-match-wins JSON, last-match-wins
Bridge / native comms Strada Strada BridgeComponent + stimulusBridge
Presentation types push, modal, replace push, modal, replace default, modal, new_window, replace, native, none
JS injection WKUserScript evaluateJavascript on_page_load + eval
Rails gem turbo-rails turbo-rails turbo_desktop-rails
Binary size System WebKit ~20 MB (Chrome WebView) ~5–10 MB (OS WebView)
Platforms iOS, iPadOS Android macOS, Windows, Linux

The key insight is that every concept transfers directly: if you already know how to structure a Hotwire Native mobile app with path configuration and Strada bridge components, you already know how to use Turbo Desktop. The only difference is that the native shell is written in Rust (via Tauri) instead of Swift or Kotlin.

Quick Start

1

Clone and install dependencies

git clone https://github.com/aguspe/turbo_desktop.git
cd turbo_desktop
cargo install tauri-cli
npm install
2

Configure your Rails server URL

Edit turbo-desktop.config.json to point at your running Rails app:

{
  "server_url": "http://localhost:3000",
  "app_name": "My App",
  "user_agent": "Turbo Desktop/0.2.1 (macOS; aarch64)",
  "window": { "width": 1200, "height": 800 },
  "path_configuration_url": "http://localhost:3000/turbo-desktop/path-configuration.json"
}
3

Add the Rails gem

# Gemfile
gem "turbo_desktop-rails"
bundle install
rails generate turbo_desktop:install
4

Mount the path configuration endpoint

config/routes.rb
mount TurboDesktop::Engine, at: "/turbo-desktop"
5

Run the desktop app

cargo tauri dev

With "server": { "command": "bin/rails server" } in the config, opening the app starts your Rails server too — one command, not two terminals. A server you started yourself is left alone.

Your Rails app now runs inside a native desktop window with full Turbo Drive integration, path-configuration-based routing, bridge components, a native menu bar, and DevTools support.

Or scaffold into an existing project

# From your Rails project root
npx turbo-desktop init
npx turbo-desktop dev
